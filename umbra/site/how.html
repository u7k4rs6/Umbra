01   States

Four states. Missing data is one of them.

A transcript with no tool records gives every node the unknown state, which is the correct answer rather than a guess. Nothing here is ever an error.

01● Lit

Read with a range covering the symbol, at or after the change began. Or edited.

02◐ Penumbra

Half seen. One of the five tiers below, from a partial read down to a mention.

03○ Umbra

Nothing in the session touched the file or named it. This is what the tool exists to find.

04? Unknown

The transcript carries no tool events and no mentions, so no state can be computed.

02   Ranking

Six factors, all printed next to the node.

Every score can be recomputed by hand. That is the point of printing them.

  1. Relation weight. A direct caller is 3, a data flow or type consumer 2, a caller reached through another symbol 1.5, a co-change file 1.
  2. How much depends on it. Multiplied by 1 plus the base-two logarithm of 1 plus its own dependents.
  3. How weakly it was seen. Multiplied by 1 for umbra, 0.7 for echo, 0.6 for afterimage, 0.5 for the other penumbra tiers, 0 for lit.
  4. Far field. Multiplied by 1.5 when it sits in a different package from the symbol that changed.
  5. Fault line. Multiplied by 1.5 when the call site sits inside error handling.
  6. Tests. Plus 3 if it is a test, plus 2 if a test reaches it.
Worked by hand

test_rounding is a direct caller, so 3. No dependents of its own, so 1. Full umbra, so 1. It lives in tests/ while the change is in app/, so 1.5. Ordinary call site, so 1. It is a test, so add 3. That is 3 x 1 x 1 x 1.5 x 1 + 3 = 7.5.

The beacon override

A call site within four lines of a SAFETY, CRITICAL or INVARIANT comment is pinned to the top whatever it scored, with the comment shown. Somebody wrote that note by hand; it outranks a heuristic.

The scar factor

Opt in with --history: a file with several recent fix commits is multiplied by up to 2. Off by default because it is noisy, and printed like every other factor when it is on.

03   The pipeline

What happens when you run it.

Every input comes through documented Entire and Graph output. There is no model at any step.

  1. Resolve. Turn a checkpoint id or a commit-ish into a checkpoint, a commit and its parent, and say how the pairing was made.
  2. Check out. Detached worktrees of head and parent under the plugin data directory, never in your working tree.
  3. Load the field. A graph snapshot, the relation map from the installed capabilities, and the changed symbols from the commit.
  4. Walk it. Breadth first to the requested depth, keeping the shortest path from each dependent back to a source.
  5. Subtract. Build the examined set from the transcript's tool activity and the agent's own words, and classify every node.
  6. Probe. Select the tests that reach shadow, record a baseline on the parent, and adjudicate on the head.
  7. Sweep. Run the whole suite once and report every test the selection missed, with the reason it missed it.
04   The sweep

A selection that audits itself is worth more than one that does not.

What a leak is

A test that changed state under the edit but that selection never chose. It is reported separately from a cracked probe, because calling it a probe would name a test that was never among the probes.

Why it was missed

Each leak carries its reason: a path deeper than the search went, no resolved call edges from the test file, a path only over a relation Umbra does not follow, or nothing the graph can see at all. That is how you see the size of the gap.
